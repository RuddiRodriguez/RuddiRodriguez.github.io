Project origin: a real banking campaign-response problem

I developed the original model for highly imbalanced banking campaign data. The goal was to rank customers and use lift and gain to support a cost-based choice of whom to contact. This article describes part of the reusable workflow inspired by that work.

Keeping the modelling process together

Once loading, comparison, tuning, and validation lived in separate scripts, the next problem was keeping them connected. Each stage needed to read the intended input and leave an output the next stage could use. I separated the common procedure from dataset-specific settings: paths, outcome labels, evaluation measures, and report choices.

This article brings together three documents from the repository: the README for run order, METHODOLOGY_AND_OPTIONS.md for the behaviour of each stage, and PREPROCESSING_TECHNIQUES.md for the data transformations and their limits.

Here I follow the decisions that connect those stages. The other articles examine the functions; this one explains why their order and shared settings matter. The commands remain alongside that explanation for readers who want to follow the procedure.

Defining the question before choosing the model

I kept the reusable workflow focused on a yes-or-no outcome, encoded as 0 and 1. The workflow expects CSV files and models that follow the scikit-learn interface. It does not provide a general-purpose loader for databases, spreadsheets, or streaming data.

The configuration identifies the outcome column, raw-data file, and separate training and test files. The following is an illustrative configuration for a response project, not the repository’s current fraud configuration.

The split reserves 20% of rows for testing and keeps roughly the same outcome balance in both sets. It is a random row split. A question about future periods or unseen customers needs a suitable time-based or grouped split, which the current utility does not implement.

For fictional campaign demonstrations, create_fake_data.py generates data and then splits it. The generator uses response_label as the outcome; matching settings are required. For an existing real CSV, skip generation and start with the split.

Why preparation belongs in the modelling decision

Preprocessing turns the input columns into a representation a model can use. This project has two distinct implementations. Choosing between them affects both the transformations and the models that can be searched.

ChoiceMain flowOptional search path
Numeric columnsStandardScaler: subtract the mean and divide by standard deviation.Search StandardScaler, MinMaxScaler, RobustScaler, or no scaling.
Missing numeric valuesNo imputer added by default.Search replacement with mean, median, or most frequent value.
Text categoriesOrdinalEncoder assigns numeric codes; unseen categories receive 99999.Same fixed encoder, plus categorical missing-value replacement.
Missing categoriesNo imputer added by default.Search most frequent value or a constant placeholder.
How choices changeChange PreprocessingConfig in Python.Search choices are defined in the optional search-space code.
Model scopeBroad comparison list, then Optuna-supported candidates.Smaller subset: balanced logistic regression, balanced random forest, balanced extra trees, and histogram gradient boosting.

The default column selectors treat object columns as categories and other columns as numeric. A category stored as an integer will therefore be treated as numeric unless prepared differently. Dates need manually derived features, and free text needs separate preparation.

Ordinal codes are convenient but can introduce an artificial order. Distance-based and linear models may interpret category-code differences as meaningful. Encoder choice therefore remains a modelling decision, not something the current YAML settings automatically resolve.

Connecting the stages through their saved outputs

The main sequence starts with the split, compares and refines candidates, tunes their settings, and finally evaluates the saved pipeline. These commands show the order from the repository root; each stage reads the configured output of the previous one.

StageDecision or actionOutput to inspect
SplitSeparate training from testing.Row counts, outcome rates, and both CSV files.
CompareEvaluate candidate pipelines using cross-validation.Average score, variation across splits, and run time.
RefineRefit leading candidates and calculate training metrics.Refinement table and optional saved candidate pipelines.
Tune and fitSearch supported candidates, then fit the selected pipeline.Tuning table, parameter JSON, and fitted pipeline.
ValidateScore the test data and examine selection choices.Prediction metrics, cutoffs, ranked groups, lift/gain, and charts.
InterpretOptionally calculate importance and inspect artifacts.Importance table and the dashboard’s validation, model, and feature views.

Comparison uses cross-validation on training data. Refinement metrics are calculated on the training set itself; they help shortlist candidates and are not independent final-test results. Optuna then evaluates candidate settings through stratified cross-validation.

The comparator currently saves results sorted by roc_auc. If a different comparison scoring measure is chosen, the entry script’s sorting must also be changed. The repository documents this limitation explicitly.

Deciding how much to search and what to optimise

Several controls define how much work the search performs and what it optimises. They have different roles and should not be treated as interchangeable.

SettingRole
model_comparison.cvNumber of evaluation folds when comparing algorithms.
refinement.top_n_modelsHow many leading comparison models are refitted.
training.top_n_modelsHow many supported refined candidates are tuned.
training.n_trialsOptuna trials performed per tuned model.
training.cv_splitsEvaluation folds within each tuning trial.
training.scoringMeasure maximised during tuning.
training.refinement_sort_metricMeasure used to order candidates before tuning.
validation.thresholdFixed selection cutoff, or null for automatic selection.
validation.decilesNumber of ranking groups for lift/gain analysis.

The current Optuna search skips candidates without a defined search space. DummyClassifier and MLP can appear in comparison and refinement, but are not tuned by that path. Hyperparameter ranges are defined in Python, not supplied through YAML.

training.drop_regular_campaigns removes rows where campaign_group equals standard_campaign when that column exists. It has no effect without the column. This project-specific filter needs to match the intended training population.

Comparing preparation choices alongside model settings

training_model_grid_search.py is an alternative training path, despite its name: it uses RandomizedSearchCV. It samples combinations of supported preprocessing choices and a smaller set of model families, evaluates several measures, and refits using the configured selection measure.

The initial pipeline fills missing numeric values with the median and missing categories with the most frequent category. The search-space definitions can replace those choices and the numeric scaler. The categorical encoder remains fixed.

param_distributions supplies the supported combinations. n_iter sets the number sampled, while refit selects which evaluation measure chooses the final estimator. return_train_score also keeps training scores in the exported results.

The alternate script replaces the default tuning step. Its saved pipeline must also become the input referenced by validation.pipeline_path and feature_importance.pipeline_path; the dashboard model choices need to include it if it should be selectable there. Otherwise, a later stage could evaluate a different model from the one just trained.

The preprocessing factory also allows extra transformation or resampling steps through Python configuration. They are not YAML switches. A resampling step requires the imblearn dependency, which the preprocessing guide notes is not in the current requirements.

Returning from model scores to the business question

The original business problem involved rare campaign responses. I used lift and gain to frame the relationship between the fraction contacted and the responders captured. Campaign costs and response value then belong in the selection decision. This business framing is distinct from the scoring measure used in tuning.

Validation evaluates both a score cutoff and fixed-size groups near the top of the ranking. That separates two questions: how reliable are selected records, and how much of the positive population do they capture?

I read precision, recall, prediction errors, and lift/gain together because each answers a different question. Calibration is available when probability scores are supplied. A high ranking score alone does not establish campaign return or the financial cost of mistakes.

When validation.threshold is null, the implementation estimates a cutoff from the supplied evaluation labels. For independent final-test performance, choose the cutoff separately and fix it before the final evaluation. The current workflow does not implement nested cross-validation or cost-matrix optimisation.

Optional permutation importance measures the change in model performance when an input is shuffled. The dashboard brings those artifacts together and lets users select datasets, models, and filters. It is a Streamlit application, not an application running inside this static portfolio.

What I keep after the model has been fitted

The completed procedure produces more than one model file: it preserves the training/test split, comparison tables, candidate and tuning results, fitted preprocessing-plus-model pipeline, selected parameters, and validation reports.

Those artifacts show how the final model was reached and support another iteration without rebuilding the procedure. The same structure can be adapted to another binary CSV problem by changing its paths, outcome, and reporting settings, while reviewing the preprocessing choices for that dataset.

A model file needs its development history

The procedure leaves a fitted model, but also the split, settings, comparisons, and evaluation used to reach it. Keeping that history makes the next iteration easier to follow. Reusing the procedure still means revisiting the data assumptions; changing a file path alone does not make a new prediction question equivalent to the old one.

Examples follow the project’s source logic. Bank-derived identifiers are anonymised where needed; excerpts are not standalone scripts. The full repository remains private.
