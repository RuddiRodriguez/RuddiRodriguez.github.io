The problem: reconstruct the context of a contact

For the original campaign-response model, the training unit was a historical contact associated with a customer and account. The task was to describe that contact with relevant history and account context, then attach the observed response.

The resulting table supports a highly imbalanced response-ranking problem. Label construction and the evaluation population determine the base response rate against which lift and gain are interpreted.

SQL assembled those inputs before Python feature preparation. The following examples preserve the important joins, date comparisons, and window-function logic while replacing every source table, schema, field, and local variable with generic names. They omit bank-specific categories, fixed dates, locations, connection details, and business filters.

These are explanatory adaptations, not queries to execute against a real bank database. The generic schema names do not map to published production tables.

1. Derive recency and prior-contact counts

The original history query combines two contact sources. Within each source, window functions order each customer’s contacts by date. LAG finds the earlier contact date; ROW_NUMBER counts the contacts that precede the current row.

The first contact receives a zero gap because its missing previous date is replaced with its own date. UNION removes identical output rows. As in the original query, the windows are calculated separately for each source before the union; this does not create a single global contact sequence across both systems.

The original windows order by contact time without a separate tie-breaker. Contacts sharing that time therefore need an explicit ordering rule if the sequence must be unambiguous. @history_start is a generic illustration parameter, replacing fixed private date filters.

2. Join contact and account context

A customer can have more than one account. The original query matches both customer and account identifiers, and only accepts an account created before the historical contact. It then calculates age and selected event features relative to that contact date.

feature_stage.contact_events stands for the preceding history result. The event field represents a generic dated account event. The large numeric fallback mirrors the original “no earlier event” convention.

The status rule shown is the original date-comparison pattern, with anonymous names. A status-change date alone does not necessarily reconstruct all historical status transitions. Likewise, filtering by opened_date does not make a current snapshot fully point-in-time correct.

3. Attach customer features and response labels

The original training query adds customer attributes through a left join, retaining the history/account row even when the customer record is missing. Derived age is evaluated at the contact date. The public illustration uses a small generic subset rather than reproducing the private feature inventory.

DATEDIFF(year, ...) counts calendar-year boundaries; it is not an exact completed-years birthday calculation. The original code uses that approximation. Joining a current customer snapshot also requires review if attributes can change over time.

The original response label is attached later in Python, rather than generated by the training SQL. The logic matches customer and contact date, then removes rows without a known outcome.

This creates labelled records, but the join keys must identify the intended contact. Multiple contacts or response rows for the same customer/date can multiply records. Outcome definitions and the response observation window need to match the campaign process.

4. Reuse the SQL layer for production scoring

At scoring time, the deployment queries extract active customer and account information, calculating current-account features against the scoring date. The production preparation script also loads historical contacts and a response file.

Recent response records are excluded for a fixed maturation interval before the history is summarised. The summaries record the latest contact date, contact count, an indicator of whether any matched historical response was positive, and a communication-type aggregate. The response indicator is not the outcome of the most recent contact. Python writes these, plus account and customer extracts, to Parquet for the scoring step.

The candidate file is then joined to those cached tables. Production scoring calculates current recency and calendar features, normalises categories, selects model columns, loads the fitted pipeline, and ranks probabilities. See the production setup article for the handoff.

What the SQL design teaches

The SQL layer establishes the unit of analysis and the meaning of time-dependent inputs. Window functions supply contact-history features; joins combine operational sources; date comparisons keep selected events tied to the contact being modelled.

The archived implementation also exposes important review points: source-local histories, duplicate-sensitive joins, current snapshots used for historical enrichment, date-unit differences, and approximate age. Preserving these distinctions in the explanation is more useful than presenting an idealised query that the original system did not use.

The public examples are deliberately shortened and renamed. They explain the method without exposing the bank’s schema, identifiers, infrastructure, categories, or customer records.

What this work demonstrates

This work demonstrates SQL window functions, multi-source joins, date-relative features, and the connection between warehouse extracts and Python modelling. The examples also explain the boundaries of historical reconstruction and operational scoring.

Examples follow the project’s source logic. Bank-derived identifiers are anonymised where needed; excerpts are not standalone scripts. The full repository remains private.
