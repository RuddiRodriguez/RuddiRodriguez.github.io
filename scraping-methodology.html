WEB SCRAPING / PUBLIC-SOURCE RESEARCH / DATA QUALITY

A reusable scraping and verification workflow

Different websites need different collectors. The quality rules can stay the same: define the required evidence, keep every source, reject uncertain values, and save work in small restartable batches.

One method, different projects

A retail page, an investment firm website, and a company directory have different layouts and risks. The shared problem is deciding whether a collected value belongs in the final row. My workflow separates collection from verification so a plausible value does not become accepted data without supporting evidence.

01

Define

Set the fields, allowed sources, rejection rules, and meaning of a blank value.

02

Collect

Keep the value, page URL, collection time, and identifiers needed to match the record.

03

Match

Confirm the product, company, person, location, or store before accepting the value.

04

Classify

Mark evidence as current, historical, unresolved, unavailable, or rejected.

05

Check

Review exceptions, duplicates, missing sources, and changes outside the intended rows.

06

Checkpoint

Save small batches with a validation report so work can stop and resume safely.

The evidence rule

EvidenceTreatmentExample
Current and directly matchedAccept with its sourceAn official page names the person and publishes the address.
Current but indirectKeep for review, not as confirmedA registry phone matches, but the email appears only on another public profile.
HistoricalKeep only with a historical labelAn older company document contains an address that is no longer shown.
Masked, guessed, or unmatchedReject or leave blankA naming pattern suggests an email, but no source publishes it.

A blank field means “not supported by the required evidence.” It does not mean zero, false, or that the value does not exist.

How the method changed across three projects

ProjectMain riskVerification used
Walmart catalog scraperA valid price could belong to the wrong store or fulfilment option.Store and pickup evidence were checked before a price was saved.
Investment contact researchA current employee and a plausible email could still be the wrong combination.Role, email, and profile evidence were recorded separately; inferred addresses stayed blank.
Romanian company enrichmentLarge-scale edits could mix companies, hide uncertainty, or damage a multi-sheet workbook.Research ran in 20-row batches with source notes and workbook checks. Work paused after 960 reviewed rows when the client stopped responding.

What makes the workflow reusable

  • The requested fields and evidence rules are configuration, not assumptions hidden in the collector.
  • Every accepted value keeps enough context to trace it back to a public page.
  • Rejected and unresolved records remain visible instead of disappearing from the result.
  • Small checkpoints limit rework and provide a clear restart point.
  • Validation checks the output shape, duplicate records, required sources, and unintended file changes.

The collector still needs to be adapted when a website changes, blocks access, requires a browser, or exposes data through a different route. Reuse comes from the control process and shared output rules, not from pretending one scraper works everywhere.

Project status stays part of the data

A stopped run is not a completed dataset. The Romanian company project has a frozen, validated checkpoint with 960 reviewed rows and 19,042 blank email fields. Its next record is known, so the work can resume without presenting the partial database as complete.
