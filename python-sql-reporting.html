From databases to reports

The job: turn operational data into a useful report

I developed reporting workflows that connected SQL databases, campaign-contact records, operational activity, and an email-service API. Python handled the joins and calculations, then updated Excel reports and exported reusable tables. Related scripts also produced monthly HTML charts.

The difficult part was connecting records that used different identifiers and deciding what counted as a response. A contact, a callback, a link click, an application, and a completed outcome represent different events. A useful report needs a clear relationship between them, a time window, and a consistent counting unit.

This entry brings those related workflows together to show my experience with Python, SQL, Excel, APIs, and reporting. Code examples adapt the original logic with generic table names, columns, status values, and file locations. The small output example uses invented data.

3. Define response using event dates

A later event becomes a response when it belongs to the matched record and falls between the contact date and the end of the reporting window. Separate flags describe response, approval, and completion. The code also calculates elapsed days and the value associated with a completed outcome.

The inclusive date conditions preserve the original window logic. Generic decision and status values replace internal codes. A response flag is a reporting rule linking contact and activity; it does not establish that the contact caused the event.

4. Aggregate at the right level

A join can return multiple activity rows for one customer in one campaign. This simplified adaptation first produces one customer/campaign/channel row for each contact date. Taking the maximum of a 0/1 flag records whether that customer had the event, rather than counting every joined candidate.

The original summaries also grouped by action, channel, and status. Related reports used distinct-customer and distinct-campaign counts for monthly charts. Counting customers, contacts, or joined events answers different questions; the report must specify which one it uses.

An overlap-correction function exists in the response repository, but its call is commented out in the main report. I therefore do not present automatic correction across overlapping campaigns as an active step in that script.

5. Analyse email-service data through an API

A separate workflow added service data unavailable in the SQL tables. It used a SOAP client to request the campaign catalogue, retrieve tracking-link events, and read campaign reports. The code converted the service response into a DataFrame, then added dates and reporting periods.

The following examples retain the historical SOAP operations and field positions. The service name, account values, endpoint, and credentials are omitted. Authentication is supplied when calling the functions.

tracking_hits() totals the service’s link-hit field. This is an event count, which can include repeat interactions; it is not a count of unique responders or completed business outcomes. Campaign reports and address-history requests were also present in the source. Their fields need the service definition before assigning a business meaning.

The historical scripts included pauses between groups of requests. These examples show the request and transformation logic; they are not a claim that the archived API version has been tested against today’s service.

6. Apply selection rules and return data to SQL

Reporting and campaign preparation shared the same tools. A reminder workflow loaded a selection, joined exclusion and closed-account lists, kept eligible contactable records, then wrote the resulting table back to SQL and exported a CSV.

to_sql() shows the return path from a Python table to a database table. The replacement behaviour reflects the historical script; the generic target name is supplied by the caller. Original delivery code also emailed an exported file. This portfolio example focuses on data preparation and reporting.

The original workflows opened an existing workbook and wrote the reporting table into its data sheet. This matters when people already use a template with formatting, charts, and slicers: refreshing its input data fits their existing reporting process.
