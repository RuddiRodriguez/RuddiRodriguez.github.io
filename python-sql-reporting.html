From databases to reports

Reusable building blocks for SQL, Python, APIs, and reports — with examples from my work.

Different reports, a familiar sequence of steps

Different reporting jobs share the same core steps: get data, make its fields consistent, connect related records, apply rules, calculate summaries, and deliver the result. I used these steps across SQL databases, Python analysis, service APIs, and Excel reports.

Across those jobs, the tables and business rules changed, but much of the handling stayed the same. I could use the same sequence of small functions for a different question by changing the query, join keys, calculations, and output. Each step left a table the next one could use.

The sections below explain these common patterns first. Specific examples at the end show how I used them for response reporting, callbacks, service interaction analysis, and reminder preparation. All names and paths are generic; the downloadable sample uses invented data.

Typical flow: SQL or API → Python tables → cleaning and joins → rules and summaries → Excel, CSV, SQL tables, or HTML charts.

Starting with the records behind the question

This block turns database records into a Python table. SQL chooses the fields, filters the relevant period or population, and can join tables before returning the result. Python then receives a DataFrame: a table that can be cleaned, matched, and analysed.

Keep the query, connection, and filter values separate. That lets the same loading function serve different reports without embedding a private database name or file location.

Input: a connection, SQL query, and named filter values. Output: a Python table. The parameters correspond to placeholders such as :start_date in the query.

Some jobs also prepare database tables by running SQL files in a defined order. That uses the same separation: SQL holds the database rules; Python controls which steps run and when.

Getting the tables to agree before joining them

Dates and identifiers must have compatible formats before records can be compared. Convert date fields into dates, remove unwanted spaces, and apply any required identifier formatting. The exact cleaning rule depends on the source: removing a separator is appropriate only when it represents formatting, rather than part of an identifier.

When several files or query results share the same columns, combine them into one table. Then join that table to related records using a shared key.

Input: compatible tables and a shared identifier. Output: connected records. An inner join keeps matches; a left join also retains unmatched rows from the first table. Repeated keys can create several rows per record, so decide what one row should represent before calculating totals.

Deciding which records and events count

A report needs explicit rules: which records qualify, which events count, and which dates are relevant. Express these as conditions on table columns. Keep the rule separate from the general function that selects rows.

The same approach can create 0/1 columns for outcomes instead of removing rows. That is useful when the report needs to compare all records with the subset that met a condition. Time windows, eligibility filters, and completion rules are examples of this block; their definitions belong to the particular report.

Choosing what one row and one total mean

Choose what one observation represents before grouping: a customer, a contact, an event, or a reporting period. Then choose the appropriate calculation for each column, such as a sum, maximum, or distinct count.

Input: a table, grouping columns, and a dictionary of calculations. Output: one summary row per group. For example, a monthly report might group by month and channel, sum outcome values, and count distinct customers.

A join with several events per customer may need two summaries: first consolidate each customer’s records, then add the results across the population. A maximum of a 0/1 flag answers “did this customer have this event?”; a sum answers “how many flagged rows are there?” Rates need a numerator and denominator measured at compatible levels.

Bringing service data into the same analysis

An API provides another source of data. The common steps are to request the records, extract the fields needed for the report, convert them into a table, and join or summarise them with the other sources.

The request depends on the service. Once the fields have been extracted, the table transformation can stay simple:

Input: extracted rows and their column names. Output: a table that can use the same cleaning, joining, and summarising blocks as SQL data. Interpret fields according to the service definition: interaction events, unique people, and completed business outcomes measure different things.

How I combined these blocks in real work

Campaign-response reporting

I loaded contact history and activity from SQL, cleaned identifiers and dates, matched records, and defined responses using a contact-to-activity window. Separate flags represented response, approval, and completion. Customer-level consolidation came before campaign totals and Excel output.

These generic status values replace internal codes. The date-window rule associates an event with a contact; it does not establish that the contact caused the event. An overlap-correction function existed in the historical source, but its main-script call was commented out.

Callback and selection matching

I combined several selection batches and matched them against callbacks. In this particular source, SQL extracted an account reference from an attribute field before joining account records. The substring position belongs to that source’s format.

Email-service interaction reporting

I requested the campaign catalogue and tracking-link records through a SOAP API, converted them into tables, and added dates and reporting periods. The examples preserve historical operations and field positions, with the service endpoint and account details omitted.

Tracking-link hits can include repeat interactions. They are not unique responders or completed business outcomes. These archived request examples were not tested against today’s service.

Reminder preparation

I loaded a selected population, joined exclusion and closed-account lists, applied contactability rules, and saved the prepared selection to SQL and CSV. This combines the same loading, joining, rule, and output blocks for a different task.

What I take into the next report

These jobs kept bringing me back to the same questions: which records belong together, what one row represents, and what the output needs to explain. Small functions helped keep the handling readable, while the query and business rules gave each report its particular meaning.

The examples here adapt several historical scripts. They show shared patterns and their applications, rather than one unchanged original program. A new report can reuse the blocks, but its joins, counting rules, and output still need to match the question.
