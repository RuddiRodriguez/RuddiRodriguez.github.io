Comparing and tuning models in one reusable workflow

How I connect model comparison, candidate refinement, automated tuning, saved pipelines, and reporting into one inspectable process.

Project origin: a real banking campaign-response problem

I developed the original model for highly imbalanced banking campaign data. The goal was to rank customers and use lift and gain to support a cost-based choice of whom to contact. This article describes part of the reusable workflow inspired by that work.

Read the problem and production setup →

A fitted model was only the beginning

Fitting one classifier would give me a result, but it would not explain why I should choose it. I needed a way to compare alternatives under the same preparation, examine promising candidates, and keep the steps that led to the final model.

I built Tabular Classifier Flow around that sequence. Project-specific paths and settings live in one configuration file. Each script has a defined input and output, so a later step can pick up the previous step’s artifacts.

The current comparison list includes a simple baseline alongside logistic regression, random forests, LightGBM, XGBoost, nearest-neighbour, and neural-network models. This lets me compare different approaches within a common workflow.

Comparing models on the same footing

The business objective is a useful ranking under class imbalance. Cross-validation measures such as ROC-AUC and average precision help compare candidates, while lift and gain at relevant selection percentages explain campaign usefulness. The tuning code does not directly optimise contact cost or profit.

I compare models using cross-validation: fit and evaluate across multiple splits of the training data. Each candidate includes the same configured preprocessing, rather than comparing models on differently prepared inputs.

This small function combines the shared preprocessing with the chosen model. ModelSelector.fit then evaluates that complete pipeline with cross_val_score, recording the mean score, variation across splits, and run time.

The configured default comparison measure is ROC-AUC, which describes how well scores rank positive cases above negative ones. The comparison utility accepts a configurable scoring measure. One implementation detail matters: the comparison entry script currently sorts the output by roc_auc, so changing the scoring setting alone does not fully change that script’s ranking behaviour.

Deciding which candidates deserved a closer look

model_refinement.py reads the comparison table, selects the leading candidates, fits their pipelines, and writes a second table with prediction metrics. Candidate pipelines can also be saved for later inspection.

This refinement table uses predictions on the training data. I treat it as a candidate-selection step, not independent proof of final performance. It also supports selecting the metric used to rank candidates before tuning.

Searching settings without changing the evaluation procedure

For shortlisted models with defined search spaces, I use Optuna to try different settings. Each trial creates a full pipeline and evaluates it across class-balanced splits of the training data.

TrainingSpaces suggests settings appropriate to the model. StratifiedKFold defines shuffled, class-balanced splits with a fixed seed. The objective returns the mean score across those splits, giving Optuna one value to optimise.

The study maximises the chosen score and runs the configured number of trials. It returns the model name, best score, and selected parameters. The split seed makes the folds repeatable; the code shown does not explicitly seed the Optuna sampler, so it does not establish identical search results across runs.

Saving the preparation along with the classifier

After tuning the candidates, the main script chooses the result with the highest score. It refits that pipeline on the available training data and saves both the fitted object and its selected parameters.

The saved joblib object includes preprocessing and the model. The JSON file records the selected model, score, and parameters. Tuning results are also exported to a table, allowing the search output to be reviewed separately from the fitted artifact.

Making the comparison visible in a dashboard

The Streamlit dashboard is the reporting layer of the project. Its sidebar selects a dataset and saved model, then applies available filters. Three tabs separate validation, model comparisons, and feature importance.

The validation view includes prediction metrics, score distributions, selection-cutoff comparisons, and lift/gain charts. The model view compares saved artifact tables. An optional permutation-importance step estimates how model performance changes when a feature is shuffled.

The dashboard reads an existing importance table and displays both its chart and underlying values. It skips this section when no table is present. Feature importance helps inspect model dependence on inputs; it does not establish a causal relationship.

The dashboard is part of the implemented Python application. This portfolio article describes it; the GitHub Pages site does not run the Streamlit application.

Keeping the trail behind the final model

The resulting chain produces separate data files, comparison and refinement tables, candidate models, tuning results, a selected fitted pipeline, and validation artifacts. Paths and key settings are configurable, so the sequence can be reused for another binary classification dataset.

The reusable structure has boundaries: input is CSV, the outcome must be encoded as 0/1, and models must follow the expected scikit-learn interface. A new algorithm needs a registry entry and, when tuned, an appropriate search space.

These files let me revisit the modelling decisions. They are evidence of the development process; deployment and business impact need their own evidence. The next article examines how I validate and explain predictions.

Why I kept the intermediate results

The saved comparison and tuning tables matter because the selected pipeline cannot tell the whole story on its own. They let me inspect which candidates were tried and how the choice was made. Validation then asks a different question: how useful that model is on the evaluation population and at the selection sizes that matter.

Examples follow the project’s source logic. Bank-derived identifiers are anonymised where needed; excerpts are not standalone scripts. The full repository remains private.
