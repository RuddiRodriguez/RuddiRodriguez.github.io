From SharePoint files
to one SQL table.

I built a Python workflow that brings a shared project file and historical database records into one table. It downloads the file, retrieves older records, applies a date boundary, prepares the combined data, and refreshes an Azure SQL destination.

Connect two sources with different roles

A shared file can hold current project information while an older database holds the history. Bringing both into one destination makes that information available through a common database table.

In this project, SharePoint supplies the downloaded file, SQL supplies historical project records, and Python controls the sequence between them. Azure SQL is the destination. The central task is deciding which historical records to keep alongside the file before refreshing that destination.

The description below follows the reviewed implementation. Code excerpts are shortened, anonymised adaptations: company names, internal table names, identifiers, paths, and connection settings are omitted. They explain the relevant steps rather than provide a standalone application.

Two inputs, one refreshed destination

The main script performs these steps in order. It downloads the SharePoint file, reads the historical database and the destination date range, filters historical rows, reads the downloaded bytes as CSV, and combines the sources. It then prepares values and writes the complete result.

This is a batch refresh: one execution processes the available inputs. The reviewed code does not include a scheduler or a continuously running synchronisation service.

Download the shared file into memory

The active SharePoint method connects to the configured site with credentials, requests the configured file, and returns its contents as bytes. The main script wraps those bytes in an in-memory buffer and reads them into a pandas DataFrame, which is a table Python can manipulate.

The variables represent caller-supplied settings; no real site, file location, username, or password is shown. The archived implementation reads SharePoint credentials from environment settings.

The active reader is pd.read_csv. A log message mentions Excel, but that message does not change the reader. The flow described here therefore uses CSV; an Excel workbook would require a corresponding reader change.

Shape historical records in SQL

The historical query does more than retrieve one table. It connects request records with related user, project status, country, project, and analysis information. It selects a common set of output fields, supplies defaults for some missing fields, and derives dates and project duration.

This is where much of the source-specific meaning lives. SQL prepares the historical records for combination with the file. Python reads the query result into a DataFrame through the database helper.

The query and connection settings are supplied separately. The reviewed historical query contains a filter for one particular project. That limits the rows returned in this snapshot; it should not be described as retrieving every historical project.

Matching column names matter when the two sources are combined. pandas aligns columns by name. Different names create separate columns with missing values where a source has no corresponding field; concatenation alone does not resolve those differences.

The existing table determines the historical cutoff

Before combining the sources, the script queries the destination table for its earliest and latest request dates. It uses the earliest date as a boundary and keeps historical records strictly before it.

For example, suppose the destination’s earliest request is 1 June. The filter retains historical requests before 1 June, excludes historical requests on or after that date, and then adds every row from the downloaded file. These dates are illustrative, not values from the private system.

The cutoff comes from the existing destination, not from the downloaded CSV. The code therefore depends on the destination already containing an appropriate date boundary. It has no dedicated initial-load path for an absent or empty destination.

The latest request date is retrieved but does not control the active selection. A commented-out alternative mentions filtering newer records; the executed flow uses the earliest-date boundary described above.

Combine rows, then prepare values for SQL

Once the earlier historical portion is selected, the script places those rows together with all rows from the SharePoint CSV. This is a vertical combination: it adds rows from both sources to one table. It does not match individual records by project ID or update matching records field by field.

ignore_index=True gives the combined rows a new sequential index. The date conversion prepares the expected start field as a date/time value. Columns stored as general Python objects are converted to strings.

The implementation also builds a dictionary of SQL types from the resulting column types: text maps to VARCHAR, date/time values to DateTime or Date, floating-point values to Float, and integers to INT. This makes the intended output types explicit when writing the table.

These conversions are narrow preparation rules. They do not constitute a full validation of every field. In particular, converting an object column to strings can turn missing values into text representations. There is no explicit duplicate-removal or conflict-resolution step after the combination.

Refresh the complete Azure SQL table

The export helper creates a SQLAlchemy connection for SQL Server and passes the prepared DataFrame to to_sql. The main script requests replacement of the destination table.

if_exists="replace" means the existing table is dropped and recreated with the combined dataset. It is a complete refresh, rather than an append of only new records. The output dictionary describes the newly written columns; the excerpt does not preserve or recreate existing database keys and indexes.

The destination’s previous contents influence the historical cutoff, but they are not themselves copied wholesale into the output. The replacement dataset comes from the filtered historical query plus the downloaded file. An incomplete file can therefore affect what remains in the refreshed destination.

Logging records the major steps: download, reading, transformation, type preparation, and export. The final row-count message describes “new projects,” but its calculation counts the entire combined DataFrame. It is a total output count, not a measured count of newly introduced projects.

How I describe the project

I developed a Python data-consolidation workflow that downloads a shared CSV from SharePoint, retrieves and reshapes historical project records with SQL, and combines both sources using a date boundary. It prepares values and SQL column types, then refreshes an Azure SQL destination table while logging each processing stage.

The project demonstrates connecting a document source to databases, using SQL joins and date calculations to prepare historical records, manipulating tables with pandas, and controlling a database refresh from Python. Its key design choice is the boundary between retained history and the shared file’s records.
