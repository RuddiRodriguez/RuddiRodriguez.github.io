PART 01 / DATA PREPARATION

Preparing data for a reusable classification workflow

How I built the starting point for a reusable modelling process: explicit inputs, repeatable splits, and preprocessing that travels with the model.

The problem: a repeatable starting point

A classifier learns from a table of examples to predict an outcome such as response or no response. Before comparing algorithms, I need a consistent way to read that table, identify the outcome, separate training from testing, and transform its columns.

In this project, I put those responsibilities in reusable utilities. The scripts read dataset paths and the outcome column from project settings, rather than tying every step to one dataset. The current configuration uses credit-card fraud data; a separate generator supports fictional campaign-response examples.

1. Separate inputs from the outcome

The CSV loader returns two objects: the columns available to the model and the outcome it should learn to predict. Keeping that separation explicit prevents the outcome column from becoming an input feature.

The function checks that the file and target column exist. It then removes the target from the input table and returns it separately. Here, x_data contains the inputs; y_data contains the known outcomes.

2. Reserve records for testing

I create training and test files before fitting models. The current settings allocate 80% of rows to training and 20% to testing. A fixed random seed makes that split repeatable for the same input data.

When stratification is enabled, the split preserves roughly the same balance of positive and negative outcomes in both sets. This matters when positive responses are uncommon.

validate_columns checks for the target. stratify_values provides the outcome labels used to preserve the class balance. The function returns tables with fresh row indexes; write_train_test_data saves them as separate CSV files.

3. Handle numeric and categorical columns

A dataset may mix amounts, ages, and text categories. My preprocessing factory applies a separate transformation to each column type: numeric values are scaled, while text categories receive numeric codes.

The defaults use StandardScaler and OrdinalEncoder. The encoder assigns a reserved code to previously unseen categories, so new category values have a defined representation.

The configuration supplies both the transformation and its column selector. The default selectors distinguish object columns from the remaining columns. Unselected columns are passed through. This is configurable preparation, not automatic cleaning of every possible dataset.

The factory appends the model to the preprocessing steps. Fitting the combined pipeline learns the transformations from the fitting data and reuses them for prediction. The same structure is used during model comparison and tuning.

4. Demonstrate the flow with fictional contact histories

The campaign generator creates fictional customer profiles and sequences of contacts. Features include the number of earlier contacts, time since the last contact, and previous response. After adjusting generated outcomes to the requested response rate, it rebuilds the previous-outcome features.

Sorting by customer and date establishes the contact order. shift() takes the preceding outcome within each customer’s history. First contacts receive No_Contact. These generated histories demonstrate the workflow; they are not evidence of actual customer behaviour.

Design choices and limits

The implemented split shuffles rows. It does not keep every customer in only one set and does not reserve a later period. For repeated-customer or future-response questions, a customer-based or time-based split would be a separate design decision.

Category codes also do not imply that categories have a meaningful numeric order. Missing-value treatment, date conversion, and the choice of encoding need to match the dataset and model. These are places to adapt the preprocessing configuration.

The campaign generator names its outcome Responsflag. Its settings must match that name before using the generated data. The result of this stage is a reproducible data split and a shared preparation pipeline, ready for the model-development stage.

What this work demonstrates

This part demonstrates my work in reusable data loading, class-balanced splitting, configurable preprocessing, and synthetic-data generation. The implementation connects preparation to the model pipeline so later stages can use the same process.
